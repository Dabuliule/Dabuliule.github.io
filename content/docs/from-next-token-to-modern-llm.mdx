输入“我今天喝”，模型接出“茶”。我们已经在[上一篇的小型 GPT 实验](/docs/from-character-prediction-to-tiny-gpt)里做到了这件事。可是，当别人谈到 temperature、KV Cache、RoPE、GQA 时，这个熟悉的过程突然又变得陌生了。

问题不在于少记了几个缩写，而在于还没有把它们放回各自解决的问题里。

**这一阶段的目标只有一条：能解释一个 prompt 进入 LLM 后，怎样一步一步生成后面的 token，以及这个过程为什么要这样实现。** 本文始终沿着“我今天喝”这条线走。遇到瓶颈，再引入解决它的技术。

## 阅读地图：先知道我们在解决什么

把 LLM 想成一个不断续写的人。首先要把文字变成它能处理的编号；然后根据前文给候选答案打分；接着选一个答案；最后把答案接到前文后面，再做一遍。

```text
文本 → tokenizer → token IDs → 模型 → logits → 选择一个 token
                      ↑                              │
                      └──────── 追加到前文 ──────────┘
```

在这条路上，问题依次出现：

| 遇到的问题 | 引入的办法 | 它所在的位置 |
|---|---|---|
| 字符太碎，整词词表又装不下所有词 | 子词切分、BPE、字节表示 | 模型之前 |
| 模型怎样从文本中学会预测 | 标签错位、因果语言建模、交叉熵 | 训练时 |
| 每次都选第一名会不会太固定 | 温度、top-k、top-p、采样 | logits 之后 |
| 每生成一个 token 都重算前文太浪费 | KV Cache、prefill、decode | 推理过程 |
| 缓存随上下文增长，内存不够 | MQA、GQA | Attention 内部 |
| Attention 怎样利用位置关系 | RoPE | Q、K 参与点积之前 |
| 特征尺度怎么控制，特征怎么加工 | RMSNorm、SwiGLU | Transformer Block 内部 |
| 注意力中间矩阵太大 | FlashAttention | Attention 的计算方式 |
| 想增加参数，又不想每个 token 用全部参数 | MoE | 通常替换 FFN |

前七项是本阶段**必须掌握**的内容。FlashAttention 和 MoE 先理解动机、关键计算与代价；CUDA 内核、分布式专家训练和长上下文扩展配方暂时跳过。

文章较长，建议按“输入与训练 → 生成与缓存 → 模型内部 → 效率与整合”分四次阅读。每节先跟着算一个例子，再运行代码，不必一次记住所有公式。

## 1. 为什么需要 tokenizer：先决定“一个预测单位”是什么

### 1.1 按字符和按整词，各自有什么问题

假设语料有 `play`、`playing`、`played`、`player`。

按字符切分，`playing` 需要七个 token，序列比较长。按整词切分，四个词各占一个编号，但遇到未收录的新词就麻烦了。能不能把共同部分 `play` 留下来，再配 `ing`、`ed`、`er`？

这就是子词表示的直觉：像积木一样，常见的大块一起存，不常见的词用小块拼。

不过，**BPE 不理解词根和语法**。它通过相邻片段出现的频率学习合并规则；能否学出 `play`，取决于语料和合并次数。

### 1.2 一次 BPE 合并到底发生了什么

先将四个词拆成字符，每个词出现一次。相邻对 `(p,l)`、`(l,a)`、`(a,y)` 都各出现四次。假设平局时约定先选 `(p,l)`：

```text
[p,l,a,y]       → [pl,a,y]
[p,l,a,y,i,n,g] → [pl,a,y,i,n,g]
[p,l,a,y,e,d]   → [pl,a,y,e,d]
[p,l,a,y,e,r]   → [pl,a,y,e,r]
```

然后要**重新统计**。因为 `p`、`l` 已经变成 `pl`，旧的相邻关系改变了。接着可以合并 `(pl,a)`，再合并 `(pla,y)`。这时才得到共同的 `play`。

下面只演示“应用一条合并规则”。从左向右扫描，命中两个相邻片段就合成一个，并向前移动两格，因此不会重叠合并。

```python
# 可运行片段：BPE 的一次合并
import math
import torch
from torch import nn
import torch.nn.functional as F

torch.manual_seed(42)
torch.set_num_threads(1)

def merge_pair(tokens, pair):
    result = []
    i = 0
    while i < len(tokens):
        if i + 1 < len(tokens) and tuple(tokens[i:i + 2]) == pair:
            result.append(tokens[i] + tokens[i + 1])
            i += 2
        else:
            result.append(tokens[i])
            i += 1
    return result

parts = list("playing")
for pair in [("p", "l"), ("pl", "a"), ("pla", "y")]:
    parts = merge_pair(parts, pair)
assert parts == ["play", "i", "n", "g"]
```

训练 tokenizer 时学习合并顺序；编码新文本时使用已经学到的规则及其优先级，不能为每条新输入重新统计一套词表。最后再为每个片段分配整数 ID。ID 是索引，不是词义的大小。

这里为了看清规则，按单词分别处理字符。实际 tokenizer 还可能包含规范化、预切分、特殊 token 等步骤。BPE 的子词动机可参考 [Sennrich 等人的论文](https://arxiv.org/abs/1508.07909)。

### 1.3 为什么字节词表从 256 个基本单位开始

字符种类很多，但一个字节固定是 8 个二进制位。每位只有 0、1 两种可能，因此共有：

$$
2^8=256
$$

种取值，也就是整数 0 到 255。基于字节的方案可以先把文本编码成 UTF-8 字节，再用这些字节作为基础单位。学到的合并 token 可以表示多个字节，所以**最终词表不止 256 个 token**。

这里最容易混淆的是“228 是不是一个字符”。在 UTF-8 字节流里，十进制 228 是十六进制 `E4`，它可以是一个三字节编码的起始字节，单独拿出来并不是完整 UTF-8 字符。另一方面，Unicode 码点 U+00E4 对应 `ä`。两者都是数字 228，但谈的是不同编码层次。

```python
# 可运行片段：字节、字符和码点不是同一层
encoded = "中".encode("utf-8")
assert list(encoded) == [228, 184, 173]
assert bytes([228, 184, 173]).decode("utf-8") == "中"
assert chr(228) == "ä"  # 这里把 228 当 Unicode 码点
try:
    bytes([228]).decode("utf-8")
except UnicodeDecodeError:
    pass
else:
    raise AssertionError("一个不完整的 UTF-8 前缀不能独立解码")
```

所以字节 tokenizer 的一个 token 未必独立对应可显示字符。还原文本时应先拼回字节，再解码；流式显示则需要能保留未完成字节序列的解码器。不能把每个 token 都单独 UTF-8 解码，再把结果拼起来。

**停下来想一想：** 基础字节能表示所有 UTF-8 文本，为什么还要合并？因为“能表示”和“表示得短”是两个问题。较长的 token 常能缩短序列，但词表变大会增加 embedding、输出层等开销，切分方案需要权衡。

## 2. 模型到底在学什么：把一句话拆成很多预测题

### 2.1 输入和答案为什么要错开一格

假设文本编码后是 `[1,2,3,4]`，最后补一个结束符，编号为 0：

```text
完整序列：1  2  3  4  0
输入：    1  2  3  4
答案：    2  3  4  0
```

第一个位置看到 1，预测 2；第二个位置看到 1、2，预测 3；最后看到整段文字，预测结束。

虽然训练时整段输入一次送进模型，但因果遮罩保证第 $t$ 个位置只能利用它自己和之前的位置。**并行的是计算，不是让前面的题偷看后面的答案。** 第一枚输入 token 本身若也要成为预测目标，需要另外提供 BOS 或更早的上下文；上面的简化例子没有预测它。

“语言建模”就是给文本序列建立概率模型。对已经给定的第一个 token，后续概率按条件概率连乘：

$$
P(x_2,x_3,x_4\mid x_1)
=P(x_2\mid x_1)P(x_3\mid x_1,x_2)P(x_4\mid x_1,x_2,x_3).
$$

这里不是假设各 token 独立。相反，每一项都明确依赖前面的 token。用原始文本自己的下一枚 token 当答案，从随机参数开始更新模型，就是本实验的预训练式任务。真实大规模预训练还涉及数据质量、去重、计算预算等问题。

### 2.2 logits 怎样变成概率

输出层给出一组分数，称为 logits。假设“茶、水、咖啡”的分数是 $[2,1,0]$。分数可以为负，也不要求和为 1；softmax 把它变成分布：

$$
p_i=\frac{e^{z_i}}{\sum_j e^{z_j}}.
$$

逐步代入：$e^2\approx7.389$，$e^1\approx2.718$，$e^0=1$；总和约为 11.107。三个概率约为 $[0.665,0.245,0.090]$。

指数让每一项为正，除以总和让全部概率加起来等于 1。实际计算常先减去最大的 logit，避免指数溢出：分子分母都乘同一个因子，比例不变。

### 2.3 为什么 loss 是负对数，而不直接用概率

假设两道题的正确答案概率分别是 0.5 和 0.25。模型给这两个正确答案同时出现分配的概率是：

$$
0.5\times0.25=0.125.
$$

希望它变大，就是最大似然的想法。可是训练通常写成“最小化一个 loss”，而很多小概率连乘也容易变得极小。对数刚好能把连乘变成相加：

$$
\log(0.5\times0.25)=\log0.5+\log0.25.
$$

对数在正数上单调递增，所以最大化原概率与最大化其对数方向一致；再加负号，就变成最小化：

$$
-\log0.5-\log0.25\approx0.693+1.386=2.079.
$$

单个位置的目标是正确 token 编号 $y$，于是它的 loss 是 $-\log p_y$。正确答案概率接近 1，loss 接近 0；正确答案概率接近 0，loss 越来越大。对“自信地答错”会有很强的惩罚。

多分类交叉熵通常写成 $-\sum_i y_i\log p_i$。当标签是 one-hot 时，正确类的 $y_i=1$，其余全为 0，求和就只留下 $-\log p_y$。代码可以直接传正确类的整数编号，不必真的构造 one-hot。

继续代入 softmax：

$$
-\log\frac{e^{z_y}}{\sum_j e^{z_j}}
=-\log e^{z_y}+\log\sum_j e^{z_j}
=-z_y+\log\sum_j e^{z_j}.
$$

这也解释了为什么 `cross_entropy` 接收原始 logits：它会以稳定的方式合并 log-softmax 和取正确类损失的计算。不要先对 logits 做 softmax 再交给它。

### 2.4 `[B,L,N]` 为什么要 reshape

设一次训练两句话，每句三个预测位置，词表八个 token：

```text
logits: [2,3,8] —— 3 维，一共 6 道八选一的题
labels: [2,3]   —— 2 维，每道题一个正确编号
```

为了把它交给接受 `[样本数,类别数]` 的交叉熵接口，把前两维合并：

```text
logits.reshape(-1,8): [6,8] —— 2 维
labels.reshape(-1):   [6]   —— 1 维
loss:                []    —— 0 维，单个标量
```

`-1` 表示让 PyTorch 根据元素总数推算这一维。它没有删掉时间信息；每个位置的 logits 已经由因果模型结合前文算好，现在只是将六道题排成一列批改。

```python
# 可运行片段：检查 loss 的 shape 和含义
logits = torch.zeros(2, 3, 8, requires_grad=True)
labels = torch.tensor([[1, 2, 3], [4, 5, 6]])
loss = F.cross_entropy(logits.reshape(-1, 8), labels.reshape(-1))
assert loss.ndim == 0
assert torch.allclose(loss, torch.tensor(math.log(8)))
loss.backward()
assert logits.grad.shape == (2, 3, 8)
```

因为八个分数相同，正确类概率都是 $1/8$，所以平均 loss 是 $-\log(1/8)=\log8$。对不等长序列，padding 对应的 label 可以设为 `-100`，通过 `ignore_index=-100` 排除；平均数的分母应是有效目标 token 数。右侧 padding 不会被前面的真实位置看见，但换成左侧 padding 等方案时，还要正确处理注意力遮罩和位置编号。

### 2.5 训练和生成，区别究竟在哪里

训练时答案已经在语料里，可以并行算各位置的预测，再执行 `zero_grad → backward → step` 更新参数。生成时未来答案未知，只能选出一个再往后算，通常不更新参数。

这叫自回归生成：“用自己刚生成的结果，作为下一次预测的输入”。一个从头训练的小字符模型能演示这个过程，却不能凭训练 loss 下降证明它会泛化。评估需要独立验证数据，并避免相同或近重复文本跨集合泄漏。

## 3. 模型已经给了分数，为什么还需要解码策略

### 3.1 贪心选择和抽签，是两种不同动作

继续使用概率 $[0.665,0.245,0.090]$。

贪心选择就是每次拿第一名“茶”。采样则像把转盘划成三个扇区：茶占 66.5%，水占 24.5%，咖啡占 9%。转一次可能落在水上，尽管它不是第一名。

概率是抽签规则，采样结果是一次抽签。规则完全一样，两次抽签也可能不同。

```python
# 可运行片段：同一分布，多个采样结果
scores = torch.tensor([2.0, 1.0, 0.0])  # [N=3]
probs = scores.softmax(dim=-1)         # [3]
assert scores.argmax().item() == 0
rng = torch.Generator().manual_seed(42)
draws = torch.multinomial(probs, 1000, replacement=True, generator=rng)
assert draws.unique().numel() == 3
print("1000 次采样计数：", torch.bincount(draws, minlength=3).tolist())
```

给相同实现、设备、初始随机状态和调用顺序，采样可以复现。随机种子不是模型参数，也不是温度。不要每生成一个 token 都重新设置种子；那会反复重置随机数序列。

### 3.2 温度为什么会放大或缩小概率差距

温度 $T>0$ 的做法，是先将 logits 除以 $T$，再 softmax：

$$
p_i(T)=\frac{e^{z_i/T}}{\sum_j e^{z_j/T}}.
$$

要看清差距，拿两个候选的概率做除法。它们的分母相同，会消掉：

$$
\frac{p_i(T)}{p_j(T)}
=\frac{e^{z_i/T}}{e^{z_j/T}}
=e^{(z_i-z_j)/T}.
$$

假设第一名比分数第二名高 1：

| 温度 | 第一名概率 / 第二名概率 | 意义 |
|---|---:|---|
| 0.5 | $e^2\approx7.39$ | 第一名优势很强 |
| 1 | $e^1\approx2.72$ | 原始比例 |
| 2 | $e^{0.5}\approx1.65$ | 两者更接近 |

因此“温度低，输出更固定”可以作为直觉，但机制是**分布更集中**，不是随机性消失了。只要还在采样，非第一名仍可能被选中；如果最后用 argmax，正温度不会改变分数排序，所以结果仍是第一名。

```python
# 可运行片段：温度改变分布，不改变正温度下的第一名
for temperature in [0.5, 1.0, 2.0]:
    adjusted = (scores / temperature).softmax(-1)
    print("温度", temperature, "概率", adjusted.tolist())
    assert adjusted.argmax().item() == scores.argmax().item()
```

$T$ 趋近 0 时，概率趋向最大分数对应的集合；如果唯一最大，就趋向只选它。公式不能直接除以 0。本文代码把 `temperature=0` 约定为走贪心分支，而不是执行除零。

更高温度也不是“更聪明”。它增加低分候选的机会，可能增加变化，也可能增加错误。

### 3.3 top-k：只给前几名抽签资格

假设概率为 `[0.5,0.3,0.15,0.05]`，`k=2` 保留前两项，其余变成 0。保留下来的概率总和是 0.8，因此还要重新归一化：

$$
[0.5/0.8,0.3/0.8,0,0]=[0.625,0.375,0,0].
$$

也可以直接把其他 logits 设为负无穷。因为 $e^{-\infty}=0$，随后一次 softmax 就完成过滤和归一化。

```python
# 可运行片段：严格保留 k 个候选

def top_k_probs(logits, k):
    # logits: [...,N]，最后一维为词表；返回相同 shape
    if not 1 <= k <= logits.shape[-1]:
        raise ValueError("k 必须在 1 和词表大小之间")
    values, indices = logits.topk(k, dim=-1)
    filtered = torch.full_like(logits, -torch.inf)
    filtered.scatter_(-1, indices, values)
    return filtered.softmax(-1)

base_probs = torch.tensor([0.5, 0.3, 0.15, 0.05])
assert torch.allclose(top_k_probs(base_probs.log(), 2),
                      torch.tensor([0.625, 0.375, 0.0, 0.0]))
```

`indices` 是原词表 ID，`scatter_` 把分数放回这些 ID 所在的位置。使用“低于第 k 名分数就过滤”的另一种实现，在分数并列时可能保留多于 k 项；这里明确选 k 个索引。

### 3.4 top-p：候选数量随分布变化

固定 k 有个问题：模型很确定和很犹豫时，都留同样多的候选。

top-p 先将概率从大到小排序，再保留**累计概率第一次达到阈值所需的最小前缀**。例如 `p=0.8`：

```text
分布 A：[0.90,0.05,0.03,0.02] → 留 1 个就够
分布 B：[0.40,0.25,0.20,0.15] → 0.40+0.25=0.65 不够
                              → 加上 0.20，累计 0.85，留 3 个
```

第三个必须保留，它让累计值从不足阈值跨过阈值。不能直接删除所有“当前累计值大于 0.8”的项，否则跨过阈值的这一项也被删了。

```python
# 可运行片段：保留达到阈值所需的最小前缀

def top_p_probs(logits, threshold):
    if not 0 < threshold <= 1:
        raise ValueError("阈值必须在 (0,1] 内")
    sorted_logits, ids = logits.sort(dim=-1, descending=True)
    sorted_probs = sorted_logits.softmax(-1)
    # 当前 token 之前的累计概率，还没达到阈值时就保留它。
    previous_mass = sorted_probs.cumsum(-1) - sorted_probs
    keep = previous_mass < threshold
    keep[..., 0] = True
    if threshold == 1:
        keep = torch.ones_like(keep)  # 避免累计舍入误删尾部
    filtered = sorted_logits.masked_fill(~keep, -torch.inf)
    selected_probs = filtered.softmax(-1)
    return torch.zeros_like(logits).scatter(-1, ids, selected_probs)

p = torch.tensor([0.15, 0.4, 0.2, 0.25])
actual = top_p_probs(p.log(), 0.8)
assert torch.allclose(actual, torch.tensor([0., 0.4, 0.2, 0.25]) / 0.85)
```

这段代码最后仍按原始 token ID 排列，不能把排序后的下标误当词表编号。浮点阈值边界可能受舍入影响，不同实现对恰好等于阈值的处理也可能略有差别。这里定义的是最小前缀规则。top-p 的出处是 [Nucleus Sampling 论文](https://arxiv.org/abs/1904.09751)。

本文选择先做温度缩放，再按 top-p 过滤，再采样。温度改变概率，所以也可能改变 top-p 保留的数量。策略组合的顺序应在实现中明确。

**小练习：** `[0.7,0.2,0.1]` 用 `top-k=2` 和 `top-p=0.6` 会得到相同候选吗？不会：前者留两个，后者只留第一名。某几次生成结果相同，并不能证明两个算法相同。

## 4. 每次续写都重读整篇文章，哪里浪费了

### 4.1 为什么旧 K、V 可以保留

假设 prompt 有四个 token。先用四个 token 预测第五个，再用五个预测第六个。如果每次都从头计算，前四个位置的很多工作就重复了。

在因果 Attention 中，第 $i$ 个位置只能看到不晚于 $i$ 的位置。追加第五个 token 后，前四个位置可见的内容没有变化。因此，在参数固定、位置相同、关闭 dropout 等随机训练行为时，旧位置在各层的表示不变，对应的 K、V 也不变。

这个结论可以一层层推下去：第一层旧输入没变，所以旧输出没变；第二层接收到的旧输入仍没变，旧输出也没变；后面的层同理。

对最新位置，只需要计算它自己的 Q，然后让它读取过去和当前的全部 K、V：

$$
o_{\mathrm{new}}=
\operatorname{softmax}\left(\frac{q_{\mathrm{new}}K_{\mathrm{all}}^\top}{\sqrt d}\right)V_{\mathrm{all}}.
$$

这就是 KV Cache 的根据。它保存的是输入相关的中间结果，不是新训练出来的模型参数。

### 4.2 为什么通常不缓存旧 Q

把 Q 理解成“当前要问的问题”，K 是“哪些记录与问题匹配的索引”，V 是“匹配后取回的内容”。新 token 要提一个新问题，所以需要新 Q；它要查询旧记录，所以需要旧 K、V。

旧 Q 用来计算旧位置的输出。那些输出在因果条件下不会因为追加 token 改变，而生成下一枚 token 只需要最新位置的结果，所以不用再保存旧 Q 来重做旧查询。

没有缓存时，单层全前缀 Attention 会构造 `[B,H,L,L]` 的分数；逐 token decode 时是 `[B,H,1,P+1]`。**有缓存仍要读取历史 K、V**，并没有把长上下文的计算成本变成常数。

### 4.3 prefill 和 decode 到底差在哪里

prefill 是一次处理 prompt 的多个 token，为每层填好缓存，同时输出最后位置的预测分布。它已经能选出第一枚新 token，不需要额外调用一次模型才有第一个答案。

decode 则把刚选出的 token 输入模型，利用旧缓存得到下一枚的分布。

| 动作 | 本次输入 | 调用后缓存长度 | 本次可以选出的 token |
|---|---|---:|---|
| prefill | 第 1～4 个 | 4 | 第 5 个 |
| 第一次 decode | 第 5 个 | 5 | 第 6 个 |
| 第二次 decode | 第 6 个 | 6 | 第 7 个 |

此时结果序列已经有七个 token，缓存却只有六个。第七个刚被选出来，还没进入模型，自然没有它的 K、V。如果现在停止，就不必为了“补齐缓存”再调用模型。

### 4.4 为什么带缓存的遮罩不能照搬方阵三角形

假设已有三个历史 token，本次一次追加两个。Q 长度是 2，K 长度是 5，分数 shape 是 `[B,H,2,5]`。两行对应真实位置 3 和 4：

```text
          K0 K1 K2 K3 K4
Q3        ✓  ✓  ✓  ✓  ×
Q4        ✓  ✓  ✓  ✓  ✓
```

第一个新 token 不得看到第二个新 token，但应该看到所有历史。判断规则是“key 的绝对位置大于 query 的绝对位置就屏蔽”，不是简单把 `[2,5]` 的普通上三角全部屏蔽。

```python
# 可运行片段：带历史长度的因果遮罩
past, length = 3, 2
query_positions = torch.arange(past, past + length)[:, None]  # [2,1]
key_positions = torch.arange(past + length)[None, :]         # [1,5]
future = key_positions > query_positions                    # [2,5]
assert future.tolist() == [[False, False, False, False, True],
                           [False, False, False, False, False]]
```

验证缓存是否正确，最有说服力的办法是：同一模型、同一完整前缀，比较“从头重算”和“缓存追加”得到的新位置 logits。只看生成文字是否相同不够，两个错误分布也可能碰巧选中同一个词。

### 4.5 上下文窗口限制的是什么

上下文通常按 token 数计量，不是汉字数，也不是字节数。相同文字经不同 tokenizer 编码，长度可能不同。本文小模型规定 prompt 加已生成 token 总共最多 64 个，达到上限就停止。

直接删掉缓存开头并不是本实验的解决办法。剩余表示可能已吸收被删除的历史，而且位置编号也要一致；若再从零重新编号，RoPE 的旋转关系会变化。滑动窗口需要作为明确的注意力和缓存方案来设计。

## 5. 缓存占满内存怎么办：从 MHA 到 GQA

### 5.1 先算一遍缓存成本

每层都存 K 和 V，这给出一个系数 2。每个 Tensor 的 shape 是 `[B,H_kv,P,d]`，所以总字节数是：

$$
\text{KV 字节数}=2\times\text{层数}\times B\times H_{kv}\times P\times d\times\text{每元素字节数}.
$$

例如 32 层，batch 为 1，32 个 KV 头，长度 8192，每头 128 维，用每元素 2 字节的类型：

$$
2\times32\times1\times32\times8192\times128\times2
=4,294,967,296\text{ 字节}=4\text{ GiB}.
$$

这只算 K、V，没算模型权重、其他激活和运行时开销。长度翻倍，缓存也翻倍；同时服务多条序列，还要乘 batch。

### 5.2 为什么可以让多个 Q 共享 K、V

MHA 给每个 Q 头配一组独立 K、V。若四个人分别检索四套记录，当然灵活，但记录要存四份。能否保留四个不同的问题，让部分人共用一套记录？

这就是 GQA 的直觉。四个 Q 头配两个 KV 头时：

```text
Q0 ─┐              Q2 ─┐
    ├→ K0、V0          ├→ K1、V1
Q1 ─┘              Q3 ─┘
```

共享 K、V 不等于共享注意力权重。因为 Q 不同，同样的 K 会得到不同点积分数。

拿不缩放的二维点积举例：$K$ 的两行是 $[1,0]$ 和 $[0,1]$。$q_0=[1,0]$ 得到分数 $[1,0]$，$q_1=[0,1]$ 得到 $[0,1]$。即使读取同一个 V，它们也会给两条内容不同权重。

```python
# 可运行片段：同一组 KV，不同 Q 得到不同结果
q = torch.tensor([[1., 0.], [0., 1.]])  # [两个查询, d=2]
k = torch.eye(2)                        # [两个历史位置, d=2]
v = torch.tensor([[10., 0.], [0., 10.]])
weights = (q @ k.T / math.sqrt(2)).softmax(-1)
head_outputs = weights @ v
assert not torch.allclose(head_outputs[0], head_outputs[1])
print("共享 KV 的两个查询输出：", head_outputs.tolist())
```

因此，**最终仍有四个 Q 头对应的输出**，不是因为 KV 只有两组就只剩两个输出头。

### 5.3 把 shape 从头走到底

我们的隐藏维度 $D=32$，四个 Q 头，每头 $d=8$，两个 KV 头：

```text
输入                 [B,L,32]
Q 投影 32 → 32       [B,L,32] → [B,4,L,8]
K/V 投影各 32 → 16   [B,L,16] → [B,2,L,8]
历史拼接后的 K/V      [B,2,P+L,8]
每个 Q 读对应的 KV    输出 [B,4,L,8]
交换维度并合并四个头   [B,L,32]
输出线性层            [B,L,32]
```

作为入门实现，可以把两个 KV 头显式复制成四个，让普通矩阵乘法对齐：

```python
# 可运行片段：GQA 的头映射与合并
B, L, P, d = 2, 3, 4, 8
q = torch.randn(B, 4, L, d)
k = torch.randn(B, 2, P + L, d)
v = torch.randn(B, 2, P + L, d)
expanded_k = k.repeat_interleave(2, dim=1)  # KV0,KV0,KV1,KV1
expanded_v = v.repeat_interleave(2, dim=1)
scores_gqa = q @ expanded_k.transpose(-2, -1) / math.sqrt(d)
future = torch.arange(P + L)[None, :] > torch.arange(P, P + L)[:, None]
weights_gqa = scores_gqa.masked_fill(future, -torch.inf).softmax(-1)
heads = weights_gqa @ expanded_v             # [2,4,3,8]
joined = heads.transpose(1, 2).reshape(B, L, 32)
assert joined.shape == (2, 3, 32)
```

这里持久缓存仍只存两个头，但 `repeat_interleave` 会创建临时副本。因此可以证明缓存减半，不能据此宣称已经实现最优 GQA 内核。

| 方案 | Q 头数 | KV 头数 | 直觉 |
|---|---:|---:|---|
| MHA | 4 | 4 | 每个查询头独享 KV |
| GQA 示例 | 4 | 2 | 每组查询头共享 KV |
| MQA | 4 | 1 | 全部查询头共享一组 KV |

KV 头减少，会限制 K、V 投影的独立性，但减小缓存。GQA 提供中间选择，质量和速度取决于训练与实现，不能只由 shape 推出。已有 MHA 权重也不能随便删掉一半头就保证效果不变；转换需要合理初始化与后续训练。[GQA 原论文](https://arxiv.org/abs/2305.13245)讨论了这类折中与转换。

## 6. RoPE 为什么要旋转：让匹配分数感受到相对位置

### 6.1 已经会加位置向量，为什么还要另一种办法

如果只用 token 内容做 Q、K，相同内容在不同位置可能得到相同向量。Attention 分数本身就缺少“它们相距几步”的信息。

上一篇将位置向量加到 token embedding 上。那是可行的。这里换一个设计目标：**能不能直接改造 Q、K，使两个位置的点积自然包含位置差？**

旋转提供了这个性质。想象两个钟表指针：它们各自的方向可以不同，但两根指针之间的夹角只与旋转角度之差有关。RoPE 就是给不同位置安排不同旋转角度，再用点积比较。

这只是帮助理解几何关系，不是说隐藏向量真的代表钟表。

### 6.2 先只转一个二维向量

二维向量 $[x,y]$ 可以拆成 $x$ 倍横向单位箭头和 $y$ 倍纵向单位箭头。逆时针转 $\theta$ 后：

- 横向单位箭头 $[1,0]$ 变成 $[\cos\theta,\sin\theta]$。
- 纵向单位箭头 $[0,1]$ 变成 $[-\sin\theta,\cos\theta]$。

把两部分按原来的 $x,y$ 倍数相加：

$$
[x,y]\longmapsto[x\cos\theta-y\sin\theta,\;x\sin\theta+y\cos\theta].
$$

比如 $[1,0]$ 转 90 度，得到 $[0,1]$；$[3,4]$ 转 90 度，得到 $[-4,3]$。长度仍然是 5，改变的是方向。

写成矩阵形式，是：

$$
R(\theta)=\begin{bmatrix}\cos\theta&-\sin\theta\\\sin\theta&\cos\theta\end{bmatrix}.
$$

这里的公式把向量视为列向量；代码通过逐元素操作实现同一变换，不需要真的构造每个旋转矩阵。

### 6.3 为什么点积会留下“位置差”

位置 $m$ 的 Q 转 $m\omega$，位置 $n$ 的 K 转 $n\omega$。先看最简单的内容：$q=k=[1,0]$。

旋转后分别是 $[\cos(m\omega),\sin(m\omega)]$ 与 $[\cos(n\omega),\sin(n\omega)]$。点积是：

$$
\cos(m\omega)\cos(n\omega)+\sin(m\omega)\sin(n\omega)
=\cos((m-n)\omega).
$$

从两个绝对位置，变成了位置之差。这不是仅仅“知道谁在前谁在后”：$n-m$ 的大小也会改变角度。不过余弦有周期，单个结果不能唯一反推任意距离。

对一般内容向量，推导仍成立：

$$
\begin{aligned}
(R(m\omega)q)^\top(R(n\omega)k)
&=q^\top R(m\omega)^\top R(n\omega)k\\
&=q^\top R(-m\omega)R(n\omega)k\\
&=q^\top R((n-m)\omega)k.
\end{aligned}
$$

第二行用的是“旋转矩阵的转置等于反向旋转”；第三行用的是“先转一个角度，再转另一个，等于转两者之和”。所以点积中的显式位置因素只依赖相对偏移，同时仍然依赖内容 $q,k$。

深层网络里的 $q,k$ 本身还会受上下文影响，不应把这个性质扩大成“整个模型在任何平移下输出都完全一样”。[RoFormer 原论文](https://arxiv.org/abs/2104.09864)给出了这种旋转位置表示。

### 6.4 一个 Q 明明有很多维，怎么旋转

二维只是基本零件。若一个头有八维，就按相邻两维分成四对：

```text
[q0,q1]  [q2,q3]  [q4,q5]  [q6,q7]
```

每对在自己的二维平面旋转，使用不同频率。基础形式是：

$$
\omega_i=10000^{-2i/d},\qquad i=0,1,\ldots,d/2-1.
$$

$d=8$ 时，指数分别是 $0,-1/4,-1/2,-3/4$，于是频率是 $[1,0.1,0.01,0.001]$。位置 $m=10$ 对应四个角度 $[10,1,0.1,0.01]$，单位是弧度。

高频变化快，低频变化慢，不同组提供不同尺度的位置信号。10000 是一种设计选择，不是唯一正确常数；改变频率配置也不是自动获得无限长上下文的证明。

**必须偶数的是参与这种配对旋转的维度。** 全头都旋转时，每头维度需要是偶数。若只旋转一个偶数维子空间，其余维度可以不转，但那是另一个明确的设计，不是给奇数维随手补零就等价。

### 6.5 `positions[:, None]` 到底做了什么

设三个 token 的位置是 `[0,1,2]`，四对维度的频率是 `[1,0.1,0.01,0.001]`。我们要让**每个位置乘上每个频率**，得到三行四列的角度表：

```text
             频率1    频率0.1   频率0.01   频率0.001
位置0          0         0         0           0
位置1          1         0.1       0.01        0.001
位置2          2         0.2       0.02        0.002
```

原来的 `positions` shape 是 `[3]`，`positions[:, None]` 是 `[3,1]`：冒号取全部元素，`None` 新增一条长度为 1 的轴。数值没有变，只是从一维列表变成三行一列。

`frequencies[None, :]` 则是 `[1,4]`。两者相乘时，广播把单列与单行配对，形成 `[3,4]`。这是一个外积式的逐项乘法，不是矩阵乘法，也不是把原位置复制成某种新位置。

```python
# 可运行片段：多维 RoPE 与广播

def apply_rope(x, positions):
    # x: [B,H,L,d]；positions: [L]；返回同 shape
    d = x.shape[-1]
    if d % 2:
        raise ValueError("本实现旋转整个头，d 必须是偶数")
    frequencies = 10000.0 ** (-torch.arange(0, d, 2, device=x.device).float() / d)
    angles = positions[:, None] * frequencies[None, :]  # [L,d/2]
    cos = angles.cos()[None, None, :, :].to(x.dtype)    # [1,1,L,d/2]
    sin = angles.sin()[None, None, :, :].to(x.dtype)
    even = x[..., 0::2]                                # [B,H,L,d/2]
    odd = x[..., 1::2]
    out_even = even * cos - odd * sin
    out_odd = even * sin + odd * cos
    pairs = torch.stack([out_even, out_odd], dim=-1)    # [B,H,L,d/2,2]
    return pairs.flatten(-2)                           # [B,H,L,d]

x = torch.randn(2, 4, 3, 8)
rotated = apply_rope(x, torch.arange(3))
assert rotated.shape == x.shape
assert torch.allclose(rotated.square().sum(-1), x.square().sum(-1), atol=1e-5)
# 同时平移 Q、K 的位置，固定内容向量时点积不变。
q_content, k_content = torch.randn(1, 1, 1, 8), torch.randn(1, 1, 1, 8)
def rotated_dot(m, n):
    return (apply_rope(q_content, torch.tensor([m])) *
            apply_rope(k_content, torch.tensor([n]))).sum()
assert torch.allclose(rotated_dot(2, 5), rotated_dot(12, 15), atol=1e-5)
```

`stack` 的最后一维把每对的新偶数分量、新奇数分量放在一起，再 `flatten(-2)` 恢复八维。若直接拼接所有偶数结果再接所有奇数结果，顺序就不是这里约定的配对格式了。其他配对布局也可以使用，但权重约定和实现必须一致。

### 6.6 旋转会不会把内容“转丢了”

已知位置时，反向旋转就能还原，所以旋转本身是可逆的，且保留向量长度。模型不需要从单个旋转结果里同时唯一恢复“内容是什么、位置是多少”；它需要的是在匹配计算中利用位置关系。

多组频率可以缓解单一周期的歧义，但这不意味着任意距离都能被完美辨认，更不意味着未训练过的超长文本一定能处理好。可计算某个位置的角度，与模型能有效利用那个位置，是两回事。

### 6.7 RoPE 和缓存怎样配合

假设已有五个 token 缓存，新 token 的真实位置就是 5，而不是因为本次输入只有一个就重新当成位置 0。

处理顺序是：投影新 Q/K/V → 按真实位置旋转新 Q/K → 将旋转后的新 K 和未旋转的新 V 接到旧缓存 → 做 Attention。旧 K 已经转过一次，不要再次旋转。通常这里不旋转 V，让显式位置关系进入匹配分数，再用这些权重读取内容。

GQA 下 Q 有四个头、K 只有两个头也不影响这段广播：`cos/sin` 的头维为 1，会分别广播到各自的头数。

## 7. RMSNorm 为什么出现：先管住尺度，再继续加工

### 7.1 同样的方向，为什么尺度也值得关心

考虑两个隐藏向量 `[3,4]` 和 `[30,40]`。它们方向相同，但长度差十倍。如果后续 Q、K 都随输入变大十倍，点积就可能变大一百倍，使 softmax 非常集中。

这不是说向量长度永远没有意义，而是说我们希望在多层计算中控制输入尺度，让后续层在较稳定的范围里工作，再让模型学习需要的缩放。

归一化的直觉类似统一量纲：不是直接拿一组很大、一组很小的数字去比较，而是先给每个 token 的特征向量建立相近的尺度基准。

### 7.2 从 `[3,4]` 算出 RMS

RMS 是均方根，名称就是步骤：先平方，再平均，最后开根号。

$$
\operatorname{RMS}([3,4])=\sqrt{\frac{3^2+4^2}{2}}
=\sqrt{12.5}\approx3.536.
$$

各分量除以它，得到约 `[0.849,1.131]`。对于 `[30,40]`，RMS 也是原来的十倍，除完之后还是同一组数。

再加入防止分母为零的小量 $\epsilon$ 和可学习缩放 $\gamma_i$：

$$
y_i=\gamma_i\frac{x_i}{\sqrt{\frac1D\sum_{j=1}^D x_j^2+\epsilon}}.
$$

$\epsilon$ 放在根号里面；$\gamma$ 有 $D$ 个参数，初始可设为全 1。它对不同特征维度学习不同缩放，不是每个 token 独立维护一份参数。

```python
# 可运行片段：沿最后一维做 RMSNorm
class RMSNorm(nn.Module):
    def __init__(self, width, eps=1e-6):
        super().__init__()
        self.scale = nn.Parameter(torch.ones(width))  # [D]
        self.eps = eps

    def forward(self, x):
        # x: [B,L,D] 或其他以 D 为最后一维的 shape
        mean_square = x.square().mean(dim=-1, keepdim=True)  # [B,L,1]
        return x * torch.rsqrt(mean_square + self.eps) * self.scale

norm = RMSNorm(2)
a = torch.tensor([[3., 4.]])
b = torch.tensor([[30., 40.]])
assert torch.allclose(norm(a), norm(b), atol=1e-6)
assert norm(a).mean().item() > 0  # 没有减均值，不要求输出均值为 0
```

这里用 float32 讲清计算。低精度模型实现还需要考虑归约精度，例如先用 float32 算平方均值，再转回输入类型，避免数值范围问题。

### 7.3 它与 LayerNorm 究竟差哪一步

LayerNorm 先求均值 $\mu$，再对偏离均值的量归一化：

$$
\operatorname{LN}(x)_i=\gamma_i\frac{x_i-\mu}{\sqrt{\frac1D\sum_j(x_j-\mu)^2+\epsilon}}+\beta_i.
$$

对 `[3,4]`，均值是 3.5，中心化后是 `[-0.5,0.5]`，忽略小量得到 `[-1,1]`。RMSNorm 没有中心化，仍得到两个正数。这种差别是算法本身，不是实现误差。

RMSNorm 保留了尺度控制，省去均值中心化；它不是“把 LayerNorm 的名字换一下”，也不能把任意已训练模型里的 LayerNorm 直接替换就保证效果相同。[RMSNorm 论文](https://arxiv.org/abs/1910.07467)研究了这个简化。实际速度收益还取决于内核、硬件与模型，本文不做性能结论。

我们的 Block 在 Attention 和 FFN 之前分别做 RMSNorm，计算后仍通过残差连接加回原表示。这让每个子模块处理归一化后的输入，同时保留一条原表示的传递路径。

## 8. SwiGLU 的 up、down 和 gate 各在干什么

### 8.1 Attention 读完前文，还需要什么

Attention 的主要工作是跨位置收集信息。收集到的信息还需要在每个 token 内部加工，这由前馈网络 FFN 完成。

普通 FFN 可以写成：

$$
\operatorname{FFN}(x)=W_{down}\,\phi(W_{up}x).
$$

这里用列向量记法省略 bias。`up` 把维度从 $D$ 变成更宽的 $F$，`down` 再从 $F$ 变回 $D$。扩大宽度提供更多中间特征，回到 $D$ 则能与原输入残差相加。

**up 不是在末尾补零，down 也不是截掉后几维。** 两者都是可学习的线性组合。例如从二维映射到三维，可以学出 `[x1+x2, x1-x2, 2*x2]`；再映回二维时，每个输出都可以综合这三个中间值。

### 8.2 为什么再加一条 gate 分支

普通激活已经有筛选作用。SwiGLU 进一步让两条投影分别承担两个角色：一条生成内容特征，一条根据输入决定每个特征的通过强度。

想象一个调音台：一条线路提供声音内容，另一组控制量调整各通道的增益。这里内容和增益都由同一个输入算出来，并由训练共同学习，而不是人工写“遇到名词开这个开关”。

SwiGLU 的计算是：

$$
u=W_{up}x,\quad g=W_{gate}x,\quad
h=u\odot\operatorname{SiLU}(g),\quad y=W_{down}h.
$$

$\odot$ 表示逐元素相乘。同一位置、同一中间维度的两项相乘，不是矩阵乘法。

### 8.3 SiLU 从最简单的数字算起

先定义 sigmoid：

$$
\sigma(z)=\frac1{1+e^{-z}}.
$$

它把实数映射到 0 和 1 之间。SiLU 再乘回输入自身：

$$
\operatorname{SiLU}(z)=z\sigma(z).
$$

当 $z=0$ 时，sigmoid 是 0.5，但 SiLU 是 0。当 $z=1$ 时，SiLU 约为 0.731；当 $z=-1$ 时，约为 -0.269；当 $z=2$ 时，约为 1.762。

所以这里的“门”是软调制，**门值不是限定在 0～1 的概率**：它可以为负，也可以超过 1。不要把整个 SwiGLU 误画成纯粹的开关。

假设内容 $u=[2,3]$，门的线性输出 $g=[0,1]$，那么：

$$
h=[2,3]\odot[0,0.731]=[0,2.193].
$$

第一维被压为 0，第二维保留一部分。如果另一个输入让 $g$ 变了，哪一维被放大或压小也随之变化。

```python
# 可运行片段：三个投影的 shape
class SwiGLU(nn.Module):
    def __init__(self, width, inner_width):
        super().__init__()
        self.up = nn.Linear(width, inner_width, bias=False)
        self.gate = nn.Linear(width, inner_width, bias=False)
        self.down = nn.Linear(inner_width, width, bias=False)

    def forward(self, x):
        content = self.up(x)                  # [B,L,F]
        gate = F.silu(self.gate(x))            # [B,L,F]
        return self.down(content * gate)      # [B,L,D]

u, g = torch.tensor([2., 3.]), torch.tensor([0., 1.])
assert torch.allclose(u * F.silu(g), torch.tensor([0., 2.1931758]), atol=1e-6)
ffn = SwiGLU(32, 64)
assert ffn(torch.randn(2, 3, 32)).shape == (2, 3, 32)
```

### 8.4 多一条投影是不是免费增强

不是。忽略 bias，普通两投影 FFN 参数量为：

$$
D F_{old}+F_{old}D=2DF_{old}.
$$

SwiGLU 有 up、gate、down 三个投影，参数量为：

$$
DF_{new}+DF_{new}+F_{new}D=3DF_{new}.
$$

要让两者参数预算相同，令 $3DF_{new}=2DF_{old}$，消去 $D$，得到：

$$
F_{new}=\frac23 F_{old}.
$$

若普通 FFN 中间宽度是 $4D$，SwiGLU 对应约为 $8D/3$，实际可能为了硬件整齐性再取整。本文为看清 shape 选了简单尺寸，不把这种教学配置当作最优架构。

SwiGLU 通过独立投影和乘法交互增加表达方式；是否优于普通 ReLU/GELU FFN，需要在相近预算下比较训练结果，不能仅从公式断言必然更好。[GLU Variants 论文](https://arxiv.org/abs/2002.05202)提供了相关实验依据。

## 9. 把这些零件接回一个 Block

到这里，可以把现代 Block 的数据流完整写出来：

```text
输入 x [B,L,D]
  │
  ├──────────────────────────────────┐
  ↓                                  │
RMSNorm → Q/K/V 投影 → RoPE(Q,K)      │
  ↓                                  │
追加逐层 KV Cache → GQA → 输出投影     │
  ↓                                  │
相加 ←───────────────────────────────┘
  │ 得到 h [B,L,D]
  ├──────────────────────────────────┐
  ↓                                  │
RMSNorm → up/gate → SiLU 门控 → down  │
  ↓                                  │
相加 ←───────────────────────────────┘
  ↓
输出 [B,L,D]
```

用公式表达残差部分：

$$
h=x+\operatorname{Attention}(\operatorname{RMSNorm}(x)),
$$

$$
y=h+\operatorname{SwiGLU}(\operatorname{RMSNorm}(h)).
$$

Attention 这个名字在此包含投影、RoPE、缓存读取、GQA 和输出投影。每层拥有自己的参数和缓存，因为不同层的输入表示不同，不能把第一层的 KV 拿给第二层用。

完整小模型再在前面加 embedding，叠两层这样的 Block，在最后加 RMSNorm 和词表输出投影：

```text
IDs [B,L]
 → embedding [B,L,32]
 → Block 1 [B,L,32]
 → Block 2 [B,L,32]
 → final RMSNorm [B,L,32]
 → 词表投影 [B,L,N]
```

词表投影和 Attention 输出投影不是同一个层：前者负责“每个候选 token 得多少分”，后者负责“把多个头的结果融合回隐藏维度”。别因为都叫 output 就混为一谈。

完整实现放在代码包的 `04_llm/21_stage_summary/model.py`。本文不再把之前推导过的模块原封不动抄一遍；现在阅读那份文件时，每一行应该都能回答它属于哪个步骤。

## 10. FlashAttention 为什么快：问题可能在搬数据，而不只是乘法

### 10.1 一个注意力矩阵能有多大

普通实现先算 $S=QK^\top/\sqrt d$，再算 $A=\operatorname{softmax}(S)$，最后算 $O=AV$。

长度为 8192 时，单个头的 $8192\times8192$ float32 矩阵有 67,108,864 个元素，每个 4 字节，共 256 MiB。多头、多 batch、训练所需的其他中间量会继续增加开销。

GPU 的大显存能装很多数据，但在大显存与较小的片上高速存储之间来回搬运也有成本。像厨师做菜，如果每一步都要走回远处仓库拿原料，再把半成品送回去，动作熟练仍可能慢。

FlashAttention 的关键是分块和融合：让一部分 Q、K、V 在高速存储中完成更多计算，避免把完整注意力矩阵来回写入大显存。它计算标准密集 Attention 的结果，允许浮点顺序带来的微小差异；不是简单删掉低分项的近似算法。密集注意力的算术复杂度仍然是二次量级。[FlashAttention 原论文](https://arxiv.org/abs/2205.14135)重点讨论了这种 IO 代价。

### 10.2 难点：softmax 分母需要所有分数，怎么分块

先不谈 GPU，只看一个 query。假设它与两个 key 的分数是 $[0,\log2]$，对应 value 暂时用标量 $[10,20]$。

直接计算：指数是 `[1,2]`，权重是 `[1/3,2/3]`，输出为：

$$
\frac{1\times10+2\times20}{1+2}=\frac{50}{3}\approx16.667.
$$

如果两个块各只有一个分数，各自 softmax 都是 `[1]`，把结果相加就成了 $10+20=30$，显然错了。关键是**各块必须共享同一个归一化分母**。

为了数值稳定，softmax 常减去最大分数 $m$。我们维护三个量：

$$
m=\max_i s_i,\quad \ell=\sum_i e^{s_i-m},\quad a=\sum_i e^{s_i-m}v_i.
$$

最终输出就是 $a/\ell$。$m,\ell$ 是标量，$a$ 在实际 Attention 中是长度为 $d$ 的向量。

### 10.3 新块让最大值变大，旧结果怎样改口径

第一块分数 0，value 为 10。此时 $m=0,\ell=1,a=10$。

第二块分数为 $\log2$，新的最大值变为 $m'=\log2$。旧块先前的指数是按“减 0”算的，现在要统一为“减 $\log2$”：

$$
e^{s-m'}=e^{s-m}\,e^{m-m'}.
$$

因此旧的指数和与加权和，都乘修正系数 $e^{0-\log2}=1/2$。新块相对于新最大值的指数为 1：

$$
\ell'=1\times\frac12+1=1.5,
$$

$$
a'=10\times\frac12+20=25.
$$

最后 $a'/\ell'=25/1.5=16.667$，与一次性计算相同。

一般更新公式就是：

$$
\begin{aligned}
m'&=\max(m,\max s_{new}),\\
\ell'&=\ell e^{m-m'}+\sum e^{s_{new}-m'},\\
a'&=a e^{m-m'}+\sum e^{s_{new}-m'}v_{new}.
\end{aligned}
$$

公式中的乘法不是技巧性“凑出来”的，而是把旧统计量换到新的指数基准下。

```python
# 可运行片段：单个 query 的在线 softmax 加权和

def online_attention(scores, values, block_size):
    # scores: [S]；values: [S,d]；返回 [d]
    m = scores.new_tensor(-torch.inf)
    total = scores.new_tensor(0.)
    weighted = values.new_zeros(values.shape[-1])
    for start in range(0, scores.numel(), block_size):
        block = scores[start:start + block_size]
        block_values = values[start:start + block_size]
        new_m = torch.maximum(m, block.max())
        correction = torch.exp(m - new_m)
        exponentials = torch.exp(block - new_m)
        weighted = weighted * correction + exponentials @ block_values
        total = total * correction + exponentials.sum()
        m = new_m
    return weighted / total

s = torch.tensor([0., math.log(2)])
values = torch.tensor([[10.], [20.]])
expected = s.softmax(-1) @ values
assert torch.allclose(online_attention(s, values, 1), expected)
# 用多个块大小检查，避免只验证一个恰巧简单的例子。
s = torch.randn(11)
values = torch.randn(11, 4)
for block_size in [1, 2, 5, 11]:
    assert torch.allclose(online_attention(s, values, block_size),
                          s.softmax(-1) @ values, atol=1e-6)
```

这段代码假设非空输入、有限分数且块大小为正，解释的是在线归一化。真实因果实现还要处理遮罩；完整代码包用每行只访问允许的 key 来演示。这里用 Python 循环跑 CPU，不是 GPU FlashAttention 内核，也没有性能加速结论。理解了“为什么可以不保存整张权重矩阵”，本阶段的目的就达到了。

## 11. MoE 为什么出现：参数可以很多，每次只用一部分

### 11.1 一个 FFN，还是多套可选 FFN

普通 FFN 的所有 token 都经过同一组权重。如果把它扩得更大，每个 token 的计算也会增加。

MoE 准备多套 FFN，叫做专家，再让 router 根据当前 token 表示选择其中少数几套。直觉像一个有多个工作台的车间：设备总数很多，但一件物品只经过被分配到的工作台。

专家名称不代表它必然学会“中文”“数学”这类人工分类。路由规律来自训练，不应把专家编号直接当成人类领域标签。

### 11.2 从两名专家算一次路由

某个 token 的 router 输出 logits `[2,1]`。softmax 后约为 `[0.731,0.269]`，top-1 选择专家 0。

假设专家 0 输出 `[10,20]`。本文的简化方案保留所选专家原来的路由概率，输出：

$$
0.731\times[10,20]\approx[7.31,14.62].
$$

为什么不是直接丢掉路由概率？因为这样路由分数仍能通过乘法影响输出，任务 loss 可向 router 传回梯度。argmax 选“哪个专家”的离散选择本身并不提供普通导数。

有些 top-k 专家方案会对选中的权重再次归一化；本文不这样做。特别是在 top-1 下，若唯一权重总被归一化成 1，仅靠这条乘法路径就无法训练 router，需要别的设计或训练信号。

```python
# 可运行片段：只调用被选中的专家
class Top1MoE(nn.Module):
    def __init__(self, width=4, expert_count=3):
        super().__init__()
        self.router = nn.Linear(width, expert_count, bias=False)
        self.experts = nn.ModuleList([
            nn.Sequential(nn.Linear(width, 8), nn.ReLU(), nn.Linear(8, width))
            for _ in range(expert_count)
        ])

    def forward(self, x):
        # x: [B,L,D]；将每个 token 独立送入 router
        flat = x.reshape(-1, x.shape[-1])         # [B*L,D]
        probabilities = self.router(flat).softmax(-1)  # [B*L,E]
        chosen = probabilities.argmax(-1)       # [B*L]
        result = torch.zeros_like(flat)
        counts = []
        for index, expert in enumerate(self.experts):
            selected = chosen == index          # [B*L] 布尔标记
            counts.append(selected.sum().item())
            if selected.any():
                output = expert(flat[selected]) # [分给这个专家的数量,D]
                weight = probabilities[selected, index, None]  # [数量,1]
                result[selected] = output * weight
        return result.reshape_as(x), counts

moe = Top1MoE()
x_moe = torch.randn(2, 3, 4)
y_moe, counts = moe(x_moe)
assert y_moe.shape == x_moe.shape and sum(counts) == 6
y_moe.square().sum().backward()
assert moe.router.weight.grad.abs().sum().item() > 0
```

`result[selected]` 的回填保留原 token 顺序。不能把各专家处理结果简单拼起来，否则 token 的位置会乱。

### 11.3 稀疏计算没有让成本消失

若有八个同样大小的专家、每个 token 只用一个，专家参数总量约是单专家的八倍，但每个 token 的专家前向只走其中一个。总模型还包括 embedding、Attention、router 等，不能把这个比例直接当作整模型速度比例。

而且全部专家权重仍要存放，负载可能集中在少数专家，多设备部署还要把 token 表示传给对应设备。因此会出现负载均衡损失、专家容量、通信与调度问题。[Switch Transformers](https://arxiv.org/abs/2101.03961)是理解 top-1 稀疏路由的一个原始参考。

本实验只验证路由、加权、回填和梯度，没有实现这些分布式机制。它也没有接入最终的小模型，避免把新训练问题混在一起。

还要区分两个名字相近的 top-k：生成时 top-k 从**词表**选候选 token；MoE top-k 从**专家集合**选内部计算分支。它们发生在完全不同的位置。

## 12. 现在完整走一遍：“我”怎样变成“我早上喝茶。”

### 12.1 先训练，再观察生成

代码包里的收尾实验使用 12 条简短中文语料，字符词表包含 EOS 和 PAD。将每句文本末尾加 EOS 后错位构造输入与 labels；右侧 padding 的 labels 设为 `-100`。两层模型从随机权重开始，通过下一 token 交叉熵训练。

核心更新过程仍是熟悉的四步，下面是完整脚本中的逻辑摘要，`inputs` 和 `labels` 由数据构造部分提供：

```python
# 逻辑摘要；完整可运行版本见代码包 run.py 的 text_demo
optimizer = torch.optim.AdamW(model.parameters(), lr=0.005)
for _ in range(200):
    optimizer.zero_grad()
    logits, _ = model(inputs)  # [B,L,N]
    loss = F.cross_entropy(
        logits.reshape(-1, vocab_size),
        labels.reshape(-1),
        ignore_index=-100,
    )
    loss.backward()
    optimizer.step()
```

这里没有把推理缓存跨训练迭代复用。每次更新后模型参数变了，旧参数算出的 K、V 不能直接当作新参数的结果。

### 12.2 生成循环里每个动作的因果关系

以一个 prompt 为例，流程如下。这里是便于阅读的伪代码，实际实现还包括参数检查与上下文限制。

```text
1. 切到 eval 模式，关闭梯度记录。
2. 编码 prompt，得到 [1,L] 的 ID Tensor。
3. prefill：logits, cache = model(prompt_ids)。
4. 取 logits[:, -1, :]，shape [1,N]。
5. 将 PAD 分数屏蔽；按贪心或温度 + top-p 选一个 ID，shape [1,1]。
6. 追加到输出序列。
7. 如果选到 EOS，或达到生成/上下文限制，就停止。
8. 否则 decode：logits, cache = model(next_id, cache)，回到第 4 步。
9. 去掉不应展示的特殊 token，将 ID 还原为文本。
```

为什么取最后位置？prompt 里的第一个位置预测第二个 token，第二个位置预测第三个；只有最后一个位置在预测 prompt 之外的下一枚。模型不是“输出整段文字再从中挑答案”，它为本次输入的每个位置各输出一组词表分数。

`eval()` 和关闭梯度不是一件事：前者调整 dropout 等层的运行行为，后者避免为推理建立反向传播记录。本模型没有 dropout，仍保留这两个习惯，使生成代码的含义明确。

### 12.3 实际观察到了什么

本地 CPU 实验固定训练种子 42，训练 200 次，观察到：

| 项目 | 结果 |
|---|---|
| 训练 loss | 约 2.9535 → 0.3092 |
| 输入 | 我 |
| 贪心生成 | 我早上喝茶。 |
| 温度 1.2、top-p 0.9、采样种子 10 | 我今天喝茶。 |
| 停止原因 | 两次都是 EOS |
| 两层、batch 2、长度 6 的 GQA 缓存 | 768 个元素 |
| 同维度四 KV 头 MHA 缓存 | 1536 个元素 |

数字可能随 PyTorch 版本、硬件和计算顺序出现差异。这些结果说明代码链路能训练、能缓存、能按策略生成；语料很小，没有独立测试集，所以不能据此得出语言能力或泛化质量结论。

低训练 loss 也不要求每个位置都预测到概率 1。比如许多句子都以“我”开头，后面可以是不同词，给定同一个短前缀本来就有多个训练答案。

### 12.4 为什么验证不能只看“它能说一句话”

完整脚本做了几类针对性检查：

- **缓存等价性：** 同时比较完整前缀重算、逐 token 追加以及一次追加两个 token 的结果。
- **GQA 头映射：** 独立按每个 Q 头读取对应 KV，检查是否错误地重复或交错分组。
- **因果性：** 修改未来 token，确认旧位置 logits 不变。
- **梯度：** 确认最终小模型的所有参数都有有限梯度。
- **停止逻辑：** 检查 EOS、禁止生成 PAD、零生成数量、长度与上下文上限。
- **独立组件：** 分块注意力对照完整计算，MoE 对照路由分配和梯度。

这些检查分别排除不同问题。例如错误的 GQA 分组若同时存在于缓存路径和完整路径里，两者也可能“等价”，所以需要独立的按头参考计算。

### 12.5 三个值得自己做的修改

**实验一：只改生成，不训练。** 固定模型和 prompt，分别用贪心、温度采样、top-k、top-p。每种采样换几个种子，记录输出。预期是分布与候选集改变，而不是模型参数改变。若只看单次输出，容易把偶然性当规律。

**实验二：故意把 decode 的位置重置为 0。** 在副本里修改 RoPE 位置，然后比较缓存与完整前缀 logits。预期不再一致。这样能直接看到“真实位置连续”是缓存正确性的条件。实验后恢复修改。

**实验三：算清参数和内存，再换结构。** 将两个 KV 头改为四个时，要同时改 K/V 投影、reshape 和分组逻辑，不能只改一个数字。预测缓存应翻倍，再检查实际元素数。比较训练质量时则需要重新训练，并控制其他配置，不能随意替换已训练权重。

## 13. 学到什么程度，才算阶段四有了一条线

不要求此时能手写 FlashAttention 内核，也不要求从零训练一个通用大模型。先合上文章，用下面这段路径检查自己有没有真正连起来：

> 文本先被 tokenizer 转成 ID。ID 经 embedding 和多层因果 Transformer 得到每个位置的词表分数。训练时用真实下一枚 token 算交叉熵并更新参数；生成时取最后位置的分数，通过贪心或采样选一个 token。prefill 处理 prompt 并建立各层缓存，后续 decode 只输入新 token。GQA 减少需要保存的 KV 头；RoPE 用真实位置旋转 Q、K；RMSNorm 控制子层输入尺度；SwiGLU 在每个位置加工特征。生成继续到 EOS 或长度限制，然后把 ID 解码回文本。

如果这段话里有一个名词只能背定义，不能解释它为什么出现，就回到对应的小实验。

### 自查题：先推，再看答案

1. 温度从 1 改成 0.5，为什么贪心选择不变，采样概率却改变？
2. prompt 有 4 个 token，已经选出了第 3 个新 token，且没有把它送回模型。缓存长度是多少？
3. 四个 Q 头共用两组 KV，最终拼接几个头的结果？为什么？
4. 新 token 的 RoPE 角度为什么不能总从位置 0 开始？
5. `positions[:, None]` 增加了新数值吗？最终角度表 shape 是什么？
6. RMSNorm 是否让向量各分量平均值为 0？
7. SwiGLU 的 gate 输出一定在 0 和 1 之间吗？
8. FlashAttention 为什么不能将各块独立 softmax 的输出直接相加？
9. MoE 的 top-1 与生成策略的 top-k，在选择什么不同的对象？

**核对推理：**

1. 除以正数不改变排序，但两个候选的概率比变成 $e^{(z_i-z_j)/T}$。
2. 缓存长 6。结果长 7，最后选出的 token 尚未计算 K、V。
3. 四个。每个 Q 仍然各自形成权重并输出一个向量；共享的是 K、V。
4. 新 Q、K 与历史 K 必须处在一致的位置体系中，否则相对角度不对应真实偏移。
5. 没有，只增加一条长度 1 的轴；`[L,1]` 与 `[1,d/2]` 广播得到 `[L,d/2]`。
6. 不会，它没有减均值。它控制的是均方根尺度，再乘可学习缩放。
7. 不一定。SiLU 是 $z\sigma(z)$，可以为负，也可以大于 1。
8. 每块独立分母不等于全局分母，必须累计指数和，并在最大值改变时修正旧统计量。
9. 前者选择内部专家 FFN，后者过滤输出词表中的候选 token。

### 接下来为什么是 SFT

到此我们已经知道模型怎样预测下一枚 token。但一个会续写文本的模型，不一定会按用户指令回答，也不一定知道多轮对话中哪些部分是用户、哪些部分是助手。

下一阶段先研究 SFT：如何把对话组织成 token 序列，怎样使用 chat template，哪些位置的 label 应参与 loss，哪些应该被 mask。优化的核心依然是下一 token 交叉熵；变化首先发生在数据和训练目标的组织方式上。

先把这件事做明白，再进入偏好学习和强化学习。阶段四建立的生成、shape 和概率基础，正是理解后训练的起点。
