很多数据库文章里都会出现一个词：

> 一致性视图。

或者换个更常见的名字：

> ReadView。

第一次看到这个词，很容易觉得它被说得太玄了。

很多人的直觉是：

> 不就是给每个数据版本加一个只会变大的 ID，然后创建视图的时候记住当前最大的 ID，以后只读取这个 ID 之前的数据吗？

这个理解不能说错。

它抓住了一致性视图最核心的一部分：

> 读数据时，不是简单读取最新值，而是要判断某个版本在当前视图下是否可见。

但它还不够完整。

因为真实数据库里，**事务 ID 递增，不等于事务提交顺序递增**。

这也是一致性视图真正复杂的地方。

---

## 一致性视图到底在解决什么问题？

先把问题放简单一点。

假设有一行数据：

```text
id = 1, balance = 100
```

现在有两个事务：

```text
T1: 把 balance 改成 200，但是还没提交
T2: 读取 balance
```

T2 读到什么？

如果 T2 读到了 200，那它读到了一个还没有提交的数据。

这就是脏读。

所以数据库至少要保证：

> 一个事务不能读到另一个事务还没有提交的修改。

再复杂一点：

```text
T1: 开始事务
T1: 第一次读取 balance = 100

T2: 把 balance 改成 200 并提交

T1: 第二次读取 balance
```

T1 第二次应该读到 100，还是 200？

这就取决于隔离级别。

如果是 Read Committed，T1 第二次可以读到 200。

如果是 Repeatable Read，T1 第二次仍然应该读到 100。

也就是说，数据库不仅要解决「能不能读到未提交数据」，还要解决：

> 一个事务在多次读取时，应该看到同一个世界，还是每条语句都看到最新已提交世界？

一致性视图就是为了解决这个问题。

它不是数据副本，而是一个判断规则：

> 对当前事务来说，某个数据版本是否可见。

---

## 它不是复制了一份快照

很多人一听「视图」或者「快照」，会以为数据库真的复制了一份数据。

比如事务开始时：

```text
把所有表复制一份
之后这个事务只读这份复制出来的数据
```

这当然太重了。

真实数据库不会这么做。

InnoDB 的思路更像是：

```text
最新记录 + undo log 历史版本 + ReadView 可见性判断
```

也就是说，数据库保留每行数据的多个历史版本。

读的时候不是直接返回最新版本，而是从最新版本开始判断：

```text
这个版本我能不能看？
不能。

那就沿着版本链找上一个版本。
这个版本我能不能看？
能。

那就返回这个版本。
```

所以一致性视图不是一份数据。

它更像是一把尺子。

这把尺子定义了：

> 哪些事务写出来的版本，对我可见；哪些事务写出来的版本，对我不可见。

---

## 只记录最大事务 ID 为什么不够？

你最开始那个理解是：

```text
每个事务都有一个递增 ID
创建一致性视图时，记录当前最大事务 ID
之后只读取事务 ID 小于等于这个最大值的版本
```

这个模型在没有并发事务时是成立的。

但只要有并发，它就会出问题。

看一个例子。

```text
T100 开始，修改 row_a，但还没提交

T101 开始，修改 row_b，并提交

T102 创建一致性视图
```

如果 T102 只记录一个最大事务 ID：

```text
max_trx_id = 102
```

那它会认为：

```text
T100 的修改 trx_id = 100，早于 102，应该可见
T101 的修改 trx_id = 101，早于 102，应该可见
```

但这是错的。

因为 T100 虽然 ID 更小，但它还没提交。

T101 虽然 ID 更大一点，但它已经提交了。

所以对 T102 来说，正确结果应该是：

```text
T100 的修改不可见
T101 的修改可见
```

这说明一个关键事实：

> 事务 ID 只能说明事务开始或分配 ID 的先后，不能直接说明它是否已经提交。

因此一致性视图不能只记录一个最大 ID。

它还必须记录：

> 创建视图那一刻，哪些事务还活着。

---

## ReadView 里真正重要的东西

在 InnoDB 里，一致性视图一般叫 ReadView。

为了理解它，可以把 ReadView 简化成几个字段：

```text
creator_trx_id: 创建这个 ReadView 的事务 ID

m_ids: 创建 ReadView 时，系统中还活跃的事务 ID 集合

min_trx_id: m_ids 中最小的事务 ID

max_trx_id: 创建 ReadView 时，系统即将分配的下一个事务 ID
```

其中最重要的是：

```text
m_ids
```

也就是活跃事务集合。

比如创建 ReadView 的那一刻，系统里还没提交的事务是：

```text
T100
T105
T108
```

下一个即将分配的事务 ID 是：

```text
T110
```

那么这个 ReadView 可以理解成：

```text
m_ids = [100, 105, 108]
min_trx_id = 100
max_trx_id = 110
```

这个 ReadView 表达的意思是：

```text
在我创建视图的时候，
100、105、108 这些事务还没有提交；
小于 100 的事务肯定都已经结束；
大于等于 110 的事务在我创建视图时还不存在。
```

这就是一致性视图的核心信息。

---

## 版本链：数据库怎么找历史版本？

现在看一行数据。

假设它最开始是：

```text
name = "A", trx_id = 80
```

后来被事务 T100 改成：

```text
name = "B", trx_id = 100
```

再后来被事务 T120 改成：

```text
name = "C", trx_id = 120
```

从逻辑上看，这行数据形成了一条版本链：

```text
C, trx_id = 120
↓
B, trx_id = 100
↓
A, trx_id = 80
```

InnoDB 里每行记录有一些隐藏字段。

这里最关键的是：

```text
DB_TRX_ID: 最近一次修改这行记录的事务 ID

DB_ROLL_PTR: 指向 undo log 中旧版本的指针
```

所以当你读取一行数据时，数据库会先看到最新版本：

```text
C, trx_id = 120
```

然后拿这个版本的 trx_id 去和 ReadView 做可见性判断。

如果 C 不可见，就通过 DB_ROLL_PTR 找到上一个版本：

```text
B, trx_id = 100
```

如果 B 也不可见，就继续找：

```text
A, trx_id = 80
```

直到找到一个对当前 ReadView 可见的版本。

所以快照读不是复制快照，而是：

```text
沿着版本链，找到当前视图下第一个可见版本。
```

## 可见性判断规则

现在问题变成：

> 给定一个数据版本，它的事务 ID 是 X。当前事务拿着一个 ReadView，怎么判断 X 是否可见？

可以按下面几条规则理解。

---

## 规则一：自己改的版本可见

如果：

```text
X == creator_trx_id
```

那么这个版本可见。

因为一个事务当然应该能读到自己刚刚改过的数据。

例如：

```sql
begin;

update user set name = 'new_name' where id = 1;

select * from user where id = 1;
```

这个 select 必须能看到自己刚刚 update 的结果。

否则事务内部连自己的修改都看不到，语义就乱了。

---

## 规则二：比所有活跃事务都老的版本可见

如果：

```text
X < min_trx_id
```

那么这个版本可见。

因为 min_trx_id 是创建 ReadView 时所有活跃事务里最小的事务 ID。

如果一个版本的事务 ID 比它还小，说明这个版本对应的事务在 ReadView 创建之前就已经结束了。

例如：

```text
m_ids = [100, 105, 108]
min_trx_id = 100

version.trx_id = 80
```

80 比 100 还小。

这说明 T80 在创建 ReadView 之前早就提交了。

所以它可见。

---

## 规则三：未来事务产生的版本不可见

如果：

```text
X >= max_trx_id
```

那么这个版本不可见。

因为 max_trx_id 表示创建 ReadView 时，系统即将分配的下一个事务 ID。

如果一个版本的事务 ID 大于等于它，说明这个版本是 ReadView 创建之后才产生的。

例如：

```text
max_trx_id = 110

version.trx_id = 120
```

T120 是当前 ReadView 创建之后才出现的事务。

对当前视图来说，它属于未来。

所以不可见。

---

## 规则四：创建视图时还活着的事务不可见

如果：

```text
min_trx_id <= X < max_trx_id
X in m_ids
```

那么这个版本不可见。

因为 m_ids 记录的是创建 ReadView 时还没有提交的事务集合。

例如：

```text
m_ids = [100, 105, 108]

version.trx_id = 105
```

说明这个版本是 T105 写出来的。

而 T105 在 ReadView 创建时还没提交。

所以这个版本不可见。

---

## 规则五：中间区间里，但不在活跃事务集合中的版本可见

如果：

```text
min_trx_id <= X < max_trx_id
X not in m_ids
```

那么这个版本可见。

这个规则一开始有点绕。

看例子：

```text
m_ids = [100, 105, 108]
min_trx_id = 100
max_trx_id = 110

version.trx_id = 103
```

103 在 100 和 110 之间。

说明 T103 在 ReadView 创建之前已经被分配过。

但 103 不在 m_ids 里。

说明创建 ReadView 的时候，T103 已经不活跃了。

既然它不活跃，又已经出现过，那就意味着它已经提交了。

所以 T103 写出来的版本可见。

---

## 把规则压缩成一句话

一致性视图的可见性规则可以压缩成这样：

```text
太老的版本，可见。
未来的版本，不可见。
创建视图时还没提交的事务，不可见。
创建视图前已经提交的事务，可见。
自己写的版本，可见。
```

这就是 ReadView 的核心。

不要把它想成一个特别神秘的东西。

它本质上就是：

```text
高水位线 + 活跃事务集合 + 自己事务 ID
```

---

## 为什么不能只看提交时间？

有人可能会问：

> 那数据库直接记录提交时间不行吗？

理论上可以。

但数据库内部已经有事务 ID、undo log、活跃事务链表等机制。

在 MVCC 里，用事务 ID 和活跃事务集合来判断可见性，成本更低，也更容易和版本链结合。

更重要的是，数据库要判断的不是简单的物理时间先后，而是：

> 当前事务的逻辑视角里，哪些版本应该存在。

这个「逻辑视角」才是一致性视图真正表达的东西。

---

## RC 和 RR 的区别：ReadView 创建时机不同

很多人学事务隔离级别时，会把 Read Committed 和 Repeatable Read 背成定义。

比如：

```text
Read Committed 解决脏读，但不能解决不可重复读。

Repeatable Read 可以解决不可重复读。
```

这当然没错。

但如果从一致性视图看，区别会非常清楚：

> RC 和 RR 的核心差异，不是可见性规则不同，而是 ReadView 的创建时机不同。

---

## Read Committed：每条语句创建一个新的 ReadView

在 Read Committed 隔离级别下，每条普通 select 都会创建一个新的 ReadView。

例如：

```sql
begin;

select balance from account where id = 1;

select balance from account where id = 1;

commit;
```

这两个 select 使用的是不同的 ReadView。

所以可能出现这种情况：

```text
第一次 select 时，T200 还没提交，所以看不到 T200 的修改。

第二次 select 时，T200 已经提交，所以能看到 T200 的修改。
```

这就是不可重复读。

用一句话说：

```text
RC = 每条语句都重新看一次最新的已提交世界。
```

---

## Repeatable Read：事务内复用同一个 ReadView

在 Repeatable Read 隔离级别下，事务里的第一次快照读会创建 ReadView，后续快照读会复用这个 ReadView。

例如：

```sql
begin;

select balance from account where id = 1;

select balance from account where id = 1;

commit;
```

第一次 select 创建了 ReadView。

第二次 select 继续使用第一次的 ReadView。

所以即使中间有别的事务提交了修改，第二次 select 仍然看不到。

用一句话说：

```text
RR = 一个事务里一直看同一个世界。
```

这就是可重复读的本质。

---

## 快照读和当前读不是一回事

这里还有一个非常容易混的点：

> 一致性视图主要服务的是快照读，不是所有读。

普通 select 通常是快照读：

```sql
select * from user where id = 1;
```

它会走 ReadView，根据版本可见性返回某个历史版本。

但下面这些不是普通快照读：

```sql
select * from user where id = 1 for update;

select * from user where id = 1 lock in share mode;

update user set name = 'x' where id = 1;

delete from user where id = 1;
```

这些属于当前读。

当前读要读取最新的已提交版本，并且通常要加锁。

原因很简单：

> 你要修改数据，就不能拿一个历史版本来改。

比如你在事务里做：

```sql
update account set balance = balance - 100 where id = 1;
```

数据库不能基于很久之前的快照版本去扣钱。

它必须面对当前最新的数据状态，并通过锁来保证并发修改的正确性。

所以要区分：

```text
快照读：读历史版本，用 ReadView 判断可见性。

当前读：读最新版本，需要加锁参与并发控制。
```

---

## 为什么 RR 下还是可能看到“新数据”？

很多人第一次接触 InnoDB 的 Repeatable Read 时，会遇到一个看起来很奇怪的现象。

事务开始后，普通 select 看不到别人新提交的数据。

但是执行 update 之后，好像又能影响到新数据。

这是因为：

```text
普通 select 是快照读。

update 是当前读。
```

RR 保证的是：

> 同一个事务里的快照读使用同一个一致性视图。

但它不意味着这个事务永远和外界隔离。

一旦你执行 update、delete、select for update，就进入当前读逻辑。

当前读要看最新已提交版本，并加锁处理并发。

所以不要把 RR 理解成：

```text
事务开始后，世界彻底静止。
```

更准确地说，它是：

```text
事务内的快照读看到的是同一个逻辑世界。
```

---

## 一致性视图和 undo log 的关系

ReadView 只负责判断：

```text
某个版本是否可见。
```

但历史版本在哪里？

答案是 undo log。

当事务修改一行数据时，InnoDB 不只是把新值写进去，还会保留旧版本的信息。

比如：

```text
原始版本：name = A, trx_id = 80

T100 修改：
当前记录变成 name = B, trx_id = 100
undo log 里保留 name = A, trx_id = 80

T120 修改：
当前记录变成 name = C, trx_id = 120
undo log 里保留 name = B, trx_id = 100
```

于是就形成了：

```text
当前记录 C
↓
undo log 中的 B
↓
undo log 中的 A
```

ReadView 负责判断哪个版本可见。

undo log 负责提供旧版本。

两者配合起来，才构成 MVCC 的快照读。

---

## 一致性视图为什么叫“一致性”？

因为它保证你读到的数据来自同一个逻辑时间点。

假设有两张表：

```text
account
order
```

一个事务正在做下单扣款：

```text
插入订单
扣减余额
提交事务
```

如果没有一致性视图，你可能出现这种读法：

```text
读 account 时，看到的是旧余额。

读 order 时，看到的是新订单。
```

这就不一致。

因为从业务语义上看：

```text
订单出现了，余额却还没扣。
```

或者反过来：

```text
余额扣了，订单却没出现。
```

一致性视图要保证的是：

> 对同一个快照读来说，你看到的多张表、多行数据，都符合同一套版本可见性规则。

它不是保证数据永远不变。

而是保证：

```text
在当前视图里，哪些版本可见这件事是稳定的。
```

---

## 用一句人话重新描述 ReadView

如果不用数据库术语，可以这样描述一致性视图：

> 当一个事务开始做快照读时，数据库会记住那一刻哪些事务已经完成、哪些事务还没完成。之后这个事务读数据时，如果某个版本是已经完成的事务写的，就能看；如果是当时还没完成的事务写的，或者是之后才出现的事务写的，就不能看。

这个描述比「拍了一张快照」更准确。

因为它没有真的拍照。

它只是记住了当时的事务状态。

---

## 再回到最初的问题

最开始那个想法是：

> 给每个数据加一个只会变大的 ID，创建一致性视图的时候记住最大的 ID。

现在可以修正成：

> 给每个数据版本记录最后修改它的事务 ID。创建一致性视图时，不只是记录一个最大事务 ID，还要记录当时仍然活跃的事务集合。之后读取数据时，根据事务 ID、活跃事务集合和版本链，找到当前视图下可见的那个版本。

所以一致性视图不是故意把简单东西说复杂。

它真正多出来的复杂度来自并发事务：

```text
有的事务 ID 小，但还没提交。
有的事务 ID 大，但已经提交。
有的版本是自己写的。
有的版本是视图创建之后才出现的。
```

只要把这些情况都处理掉，就自然会得到 ReadView 这套机制。

---

## 总结

一致性视图的本质不是快照数据，而是可见性规则。

它依赖几个关键东西：

```text
事务 ID：标记数据版本由哪个事务产生。

活跃事务集合：记录创建视图时哪些事务还没提交。

undo log：保存历史版本，让快照读可以沿着版本链回退。

ReadView：定义当前事务能看到哪些版本。
```

最终，数据库读一行数据时做的事情可以简化成：

```text
从最新版本开始看。
如果当前版本对 ReadView 可见，就返回。
如果不可见，就沿着 undo log 找旧版本。
直到找到一个可见版本。
```

所以，一致性视图不是一张照片。

它更像是数据库在某一刻写下的一句话：

> 从现在开始，对这个事务来说，哪些事务的修改算已经发生，哪些事务的修改还不算发生。
